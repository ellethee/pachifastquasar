# Internationalization

The shell uses [`@ilpachi/pachi-i18n`](https://github.com/ellethee/pachifastquasar/tree/main/packages/pachi-i18n) (vue-i18n 11, Composition API,
`legacy: false`). `createPachiApp` installs it: there is nothing else to wire.

## Languages

The shell ships `it` (reference language) and `en`. The languages offered to the user are the ones present in
the messages of the application. The initial language is, in order:

1. the choice saved in `localStorage` (`pachi-prefs-locale`);
2. the browser languages (`navigator.languages`: exact match, then base language);
3. `it`.

The fallback language is `en`. Every change is persisted, updates `<html lang>` and the Quasar language pack
(`Quasar.lang`, loaded lazily). The `PachiLocaleSwitcher` in the app bar is hidden with
`QCLI_APP_SHOW_LOCALE_SWITCHER=false` or when only one language exists.

A **fixed language** (`QCLI_APP_LOCALE=it`, `app.locale`) disables detection, persistence and the switcher
and registers only that language.

## Message layers

`composePachiMessages` merges layers; later layers win on the same key (deep merge per language):

| Layer       | Where (application)                          | Notes                                                                      |
| ----------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| shell       | inside the package (`pachiShellMessages`)    | namespaces `app`, `auth`, `menu`, `dashboard`, `errors`, `common`          |
| `generated` | `src/i18n/generated/<lang>.json`             | exported from the backend (`errors.codes.*`); do not edit by hand          |
| `overrides` | `src/i18n/overrides/<lang>.ts` or `.json`    | your corrections of generated or shell texts                               |
| `locales`   | `src/i18n/locales/<lang>.ts`                 | messages of the application                                                |
| `features`  | `src/features/<name>/locales/<lang>.ts`      | namespace = feature name in camelCase                                      |

The language code is the **file name**: `it.ts`, `en.ts`, `pt-BR.ts`. The `globs` passed to
`composePachiMessages` are the ones shown in [Getting started](getting-started.md#boot-file).

Messages are TypeScript objects, not precompiled. The Quasar preset sets `runtimeOnly: false` on
`@intlify/unplugin-vue-i18n`. In message strings the characters `{ } @ |` are special; write them with
`{'@'}`.

### Typing

`it.ts` is the reference: other languages are typed with `PachiMessages<typeof it>` so a missing key is a
compile error.

```ts
// src/features/invoices/locales/it.ts
export default {
  title: 'Fatture',
  empty: 'Nessuna fattura'
}

// src/features/invoices/locales/en.ts
import type { PachiMessages } from '@ilpachi/pachi-i18n'
import type it from './it'

const en: PachiMessages<typeof it> = {
  title: 'Invoices',
  empty: 'No invoices'
}
export default en
```

## Using translations

```vue
<script setup lang="ts">
import { useI18n } from 'vue-i18n'
const { t } = useI18n()
</script>
<template>
  <h1>{{ t('invoices.title') }}</h1>
</template>
```

Outside `setup()` (stores, helpers, Dialog and Notify callbacks) use `pachiT`:

```ts
import { pachiT } from '@ilpachi/pachi-i18n'
pachiT('common.goHome')
```

Route titles use `meta.titleKey` / `meta.descriptionKey`, resolved reactively.

Packages bring their own messages with `usePachiI18n(messages)` inside `setup()`: they are registered once
and never overwrite what the application already defined for the same key, so the application can redefine
the texts of a package.

## Adding a language in three steps

1. `pachifq new locale fr` creates `src/i18n/locales/fr.ts` and `src/features/*/locales/fr.ts` starting from
   `en.ts`;
2. translate the values (search for `TODO: translate`);
3. restart the dev server. The language appears in the switcher.

Packages in `node_modules` (including the shell) are never modified: add their keys with the same namespace in
`src/i18n/locales/fr.ts`; application messages take precedence. A package cannot add languages by itself.

## Backend error codes

A pachifast backend returns validation and business errors with a stable `code`. The frontend translates
`errors.codes.<code>` and falls back to `msg`. The translations are generated from the backend, inside the
application folder:

```bash
pachifast locale export --base-dir <backend> --dest-path src/i18n/generated --namespace errors.codes
pachifast locale export --base-dir <backend> --dest-path src/i18n/generated --namespace errors.codes --check
```

`--check` fails when the generated files are outdated, which makes it suitable for CI. A new application starts
with an empty `src/i18n/generated/` and works with the fallback texts until the first export.
