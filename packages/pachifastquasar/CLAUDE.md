# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> IN THE MONOREPO (`pachifastquasar`): this package lives in `packages/pachifastquasar`, the playground in `/playground` (root), the `dev`, `build:playground`, `typecheck:playground` commands are run from the root, with a single lockfile and `pnpm-workspace.yaml` in the root. The "sibling folders" of `settings`/`profile` are now `packages/<name>`; the other packages come from the registry (no `overrides link:`). See the root `CLAUDE.md`.

## What it is

npm package `@ilpachi/pachifastquasar` (version in `package.json`): Vue 3 / Quasar application shell (layout, optional auth, dashboard, i18n, router, HTTP client) with dependencies on the reusable `@ilpachi/*` packages (the other monorepo packages, `packages/<name>`). The repo contains the package (`src/`, Vite library mode build in `dist/`) and `playground/`, the Quasar app (`@quasar/app-vite`) that consumes it, used to develop and try it. The public documentation (English, MkDocs) lives in `docs/` + `mkdocs.yml` and is not included in the npm package (`files`); `README.md` and `CHANGELOG.md` are. A derived app depends on the package and has only a few lines of configuration (see README, "Usage in an app"). New vertical features of an app live in the APP's `src/features/**`, never in the package.

## Commands

```bash
pnpm install                          # installs root + playground (pnpm workspace; the monorepo @ilpachi packages are linked with workspace:*)
pnpm dev                              # playground: builds ./quasar, then quasar dev (package from sources, hot reload)
QCLI_AUTH_ENABLED=false pnpm dev      # without auth
pnpm test                             # unit tests (Vitest, tests/ folder, src/ alias)
pnpm typecheck                        # vue-tsc of the package
pnpm typecheck:playground             # vue-tsc of the playground
pnpm build                            # package: vite build + ./quasar entry (vite.config.node.ts) + dist/styles.css and dist/scss (scripts/build-styles.mjs)
pnpm build:playground                 # build of the package and of the playground with the package from dist/ (PACHI_PLAYGROUND_DIST=true)
QCLI_AUTH_ENABLED=false pnpm -C playground build   # playground build (package from sources)
```

The other packages are built in their own `packages/<name>` folder (`pnpm typecheck`, `pnpm build`). Publishing happens only with `pnpm release <name> <increment>` + `git push --follow-tags` (see the root CLAUDE.md): never `npm publish` by hand.

## Architecture

### Package vs playground vs derived apps vs features

- `src/` is the package: no `#q-app`, no `import.meta.glob` on app files, no `import.meta.env` (the config arrives at runtime). RELATIVE internal imports (the `src/` alias exists only for `tests/` and for the playground code).
- `src/index.ts` is the barrel (public API). Sub-paths in `exports`: `.`, `./quasar` (Node entry, `src/quasar/`, separate build: it does not import Vue), `./styles.css`, `./scss/*`.
- `playground/` (member of the pnpm workspace, depends on the package with `link:..`): `quasar.config.ts` (uses `definePachiQuasarConfig`, in dev aliases `@ilpachi/pachifastquasar` to `src/index.ts`, with `PACHI_PLAYGROUND_DIST=true` it uses `dist/`), `src/boot/pachi.ts` (`defineBoot` → `createPachiApp`), `src/router/index.ts` (`defineRouter` → `createPachiRouter` with the globs), `src/stores/index.ts`, `src/pachi-config.ts` (`pachiConfigFromEnv(import.meta.env)` + customizations), `src/i18n/generated/*.json` (backend-specific), `src/css/`, `src/features/**`.
- `packages/<name>` (monorepo): all the `@ilpachi` packages and the `pachifq` CLI are in `../<name>` relative to this package, with independent versions. The generic packages (`pachi-i18n`, `pachi-kit`) have a `dist` build with Vite library mode; the `fastquasar-*` ones (tied to the shell but autonomous in styles) and the `pachifq` CLI are workspace packages like the others. Dependencies between monorepo packages are `workspace:^` (peers with the published ranges). Components published on npm as `@ilpachi/pachi-kit` (sub-paths `/table`, `/dialog`, `/edit-dialog`, `/fields` with injectable HTTP client `setPachiFieldsHttp`, `/uploader`, `/ui`), `fastquasar-settings`, `fastquasar-profile`, `fastquasar-dashboard-widgets`, `pachi-i18n` (i18n with language selector and per-package messages), `@ilpachi/use-alova` ^2.1.0 (peer, EXTERNAL repo `ilpachi/use-alova`: alova HTTP factory with auth/overlay/errors; `createPachiApp` wires it in `src/app/create-http.ts`) (plus the `pachifq` CLI, which covers scaffolding of new projects — `pachifq create` —, new features — `pachifq new feature` — and new languages — `pachifq new locale <code>`: it generates the app from templates, which depend on the package without copying the shell sources). Each component has `peerDependencies` on `vue`/`quasar` (and on the other `@ilpachi/*` used) and is published as `dist` (`pnpm build` in the package; `pnpm typecheck` for the typecheck only). **They must not import shell services** (e.g. `pachi-kit/uploader` accepts `headers`/`eventBus` as prop/composable instead of importing `AuthManager`/`usePachiEventsStore`) — this keeps the packages installable in other projects; at most `import type` of the contracts (e.g. `PachiMenuItemFactory`). `pachi-kit/table` uses a replaceable alova factory (`setPachiAlovaFactory`). Profile, settings and dashboard widgets (activity/system) are NOT in the shell: they are the `fastquasar-profile`, `fastquasar-settings` and `fastquasar-dashboard-widgets` packages, which the package does not import. They are installed and mounted in an app feature (`src/features/<name>/routes.ts`); dependencies are injected (`setPachiSettingsOptions`, `setPachiWidgetsHttp`, `user` prop, `avatar` slot). These three packages are autonomous in styles (`--pachi-*` defaults at zero specificity): they use the project's `--pachi-*` variables if defined. The shell only keeps the minimal theme persistence (`ToggleThemeButton`, localStorage key `pachi-prefs-theme`). Routes with children show a card dashboard by default; `autoDashboard: false` (`QCLI_APP_AUTO_DASHBOARD=false`) disables it (the `/` home stays a dashboard) and `meta.dashboard` true/false decides per single route (without a dashboard the route must have a component with `<router-view>` or a `redirect`). Routes can expose `meta.widgets` (`{ component, props }[]`). Versioning and publishing: `pnpm release <name> <increment>` + `git push --follow-tags`; the GitHub Actions pipeline (`.github/workflows/ci.yml` selective, `release.yml` on tag `<name>@<version>`, trusted publishing on npmjs) does the rest.

### Runtime configuration (`src/core/config/`)

`IAppConfig` (auth, app, logo, components, menuItems, menuFactories) with defaults in `defaults.ts`; `setPachiConfig(input)` / `getPachiConfig()` are the registry read by components, stores and router (there is no longer an `appConfig` from `import.meta.env`). `pachiConfigFromEnv(env)` maps `QCLI_*`/`VITE_*` (same rules as before; the app passes `import.meta.env`). `createPachiApp` and `createPachiRouter` call `setPachiConfig` if they receive `config` (otherwise they use the one already set): the router is created BEFORE the boot files in Quasar, so the app shares the same `pachiConfig` between router and boot. The auth store resolves `storage` lazily (`lazyStorage`). Customizations: `logo` (SVG path, `img:`, component; `PachiLogo`), `components.layout|loginPage|errorPage`, `menuItems` (array or function), `menuFactories`.

### Routing (`src/router/`)

`createPachiRouter(options)` (`create-pachi-router.ts`) creates the `Router`: history from `options.mode`/`base` (`hash` default; the app passes `QUASAR_VUE_ROUTER_MODE/BASE`), tree from `buildPachiRoutes(config, { features, packages, env })` (`routes.ts`), navigation guard. The globs come from the app (`features`, `packages`, `menus`); `routes-finder.ts` contains the pure functions (ordering by `meta.order`, package name extraction, `ilpachi-<pkg>-disable-route` from `env`, `meta.root` filters). `buildPachiRoutes` composes: core routes with `meta.root === true` first, then auth (if enabled; `core/auth/pages/routes.ts` is a function of `config`), then features/packages, with a final catch-all. Routes with `meta.root === true` are top-level (outside the layout), the others are children of the layout; `meta.order` (default 99) orders the menu. Guard: auth disabled = everything passes; otherwise silent restore unless `meta.noAuth`, redirect to `/auth/login`, `authManager.canAccess(to.meta)` for per-route authorization.

### Account menu (`src/core/menu/`)

`PachiMenuItemFactory` contract (`ctx: { t, router, config, user? }` → item | array | null): a package exports `menu.{ts,js}` (or `dist/menu.js`) with the factory as default export. `collectPackageMenus(glob, env)` collects them (respects `ilpachi-<pkg>-disable-route`), `registerPachiMenus` registers them (`createPachiRouter` does it with the `menus` option), `buildMenuItems(ctx)` composes package factories + `config.menuFactories` + default items (only Home, omitted if a factory provides `/`; Profile and Settings come only from the packages) + `auth.menu.extraButtons` + `config.menuItems`, ordering by `order` (default 50). Visibility and route existence are evaluated by the component.

### Boot and v3 aliases

The shell has no boot file: `createPachiApp(ctx, { config, messages })` (`src/app/create-pachi-app.ts`, alias `pachiBoot`) sets the config, creates the HTTP client (`@ilpachi/use-alova` ^2.1.0: alova + fetch) with `token`/`authType` from `AuthManager` (token same-origin only), token refresh on 401 with `retry()`, `auto` overlay with 300 ms delay via Quasar `Loading`, error messages via Quasar `Dialog`, `cacheFor: { GET: null }` and `unwrapEnvelope` from `http.envelope` (`QCLI_HTTP_ENVELOPE=false` for backends with `PACHIFAST_ENVELOPE_ENABLED=false`) (the classes use `getUseAlovaInstance()({ url }).alova`; per-request options via `meta`: `{ meta: { autoError: false, spinner: false } }`, aliases read by use-alova), installs i18n and the `pachi-hover-fx-disabled` class. The app wraps it in `playground/src/boot/pachi.ts` (`defineBoot`). Login: `AuthManager.login` returns `{ mfaRequired }` (with MFA the `mfa_token` stays in memory only) and `verifyMfa(code)` completes the second step (`POST /api/mfa/verify`); rotating refresh tokens (the new one replaces the old one, re-read from storage for multiple tabs) and logout with `{ refresh_token }`. `createPachiApp` does `provide('pachiLogout')` (`PACHI_LOGOUT_KEY`, local logout without requests, for `fastquasar-profile` after the password change). Pinia: `createPachiPinia()` (with `pinia-plugin-persistedstate`) in the app's `src/stores/index.ts`.

`definePachiQuasarConfig(overrides?, options?)` (`src/quasar/`) is the `quasar.config.ts` preset (`pachi` boot, `css` with `~@ilpachi/pachifastquasar/styles.css`, roboto extras, SPA, `extendViteConf` with `envDir`/`envPrefix ['VITE_','QCLI_']`, `cssMinify 'esbuild'`, v2 aliases `src/ assets/ boot/ stores/ features/` (Quasar v3 no longer has them), `resolve.dedupe` of the singletons, `@intlify/unplugin-vue-i18n/vite` plugin (`runtimeOnly: false`, include `src/i18n`) and `vite-plugin-checker`, `extendTsConfig` with `src/*`, `/api` proxy to `QCLI_PROXY_TARGET`, `svg-mdi-v7` framework + Dialog/Notify/Loading/Dark). Override merge: objects recursive, arrays concatenated, `extendViteConf`/`extendTsConfig` in sequence. Structurally typed (it does not import `#q-app`). If you need a new top-level alias: `aliases` option. The playground's `tsconfig.json` is just `{ "extends": "./.quasar/tsconfig.json" }` — paths are configured in the preset.

### Logo and favicon

`pachiLogo` (`src/extras/pachi-icons/index.ts`) is `img:` + URL of `src/assets/logo/logo.svg` (Pachi mascot, fixed colors). In lib mode Vite always inlines assets as base64 (even with `assetsInlineLimit: 0`): the `pachiLogoAsset` plugin in `vite.config.ts` (with rolldown the data URL is `new URL("data:...", "" + import.meta.url)`, the regex accepts both forms) replaces the data URL with `new URL("./assets/logo.svg", import.meta.url)` and emits `dist/assets/logo.svg`; the consuming app (dev/build) resolves it with its own Vite. Do not put `?inline`/base64 back. The favicons and the regeneration commands (vtracer + svgo + inkscape) are in `src/assets/logo/` (README); the favicons go in `playground/public/` and in `pachifq/templates/app/public/`, not in the package. `pachiLogoDuotone` is deprecated.

### Styles

The layout is one viewport tall and does not scroll. Opt-in scroll: `meta.pageScroll` wraps the whole page in `.pachi-page-scroll` (vertical scroll within `--pachi-page-height`); the `PachiScrollArea` component (`src/core/components/`) scrolls only the tall content inside a page, occupying the space below itself up to the bottom limit (measures with `getBoundingClientRect`, resize + ResizeObserver).

`src/scss/` → `dist/styles.css` (compiled by `scripts/build-styles.mjs`) + `dist/scss/*` (sources). `quasar-variables.scss` (Quasar Sass palette, `!default` values: the app defines the overrides and then does `@import '@ilpachi/pachifastquasar/scss/quasar-variables'` in its own `src/css/quasar.variables.scss`), `tokens.scss` (`--pachi-*` tokens, `$dark-page/$light-page/$light-color` configurable with `@use ... with`), `app.scss` (+ blueprint/bento/quasar-hacks/...), `fonts.scss`. The styles of the `.vue` components are injected into the JS by the `vite-plugin-css-injected-by-js` plugin.

### Services (`src/services/*/`)

Common pattern: folder with `index.ts` (barrel), `<name>-manager.ts` (class/logic), `<name>-store.ts` (Pinia state), `types/` (`.ts` files, not `.d.ts`: they must reach `dist`). Present: `auth-manager` (singleton `AuthManager.getInstance()`: token/refresh with auto-renew 60s before expiry, auth header for Alova, lazy WebSocket with single-use ticket), `ws-manager`. The HTTP client (`createUseAlova`, `getUseAlovaInstance`, `ResponseError`, `STOP_PROCESSOR`) lives in `@ilpachi/use-alova` (`withFiles` from `@ilpachi/use-alova/files`): import from there. The `settings-manager` lives in `@ilpachi/fastquasar-settings`.

### i18n

Package `@ilpachi/pachi-i18n` (vue-i18n 11, composition, `legacy: false`). `createPachiApp` calls `createPachiI18n({ messages, fixedLocale, onLocaleChange: setQuasarLang })` — nothing else to wire. The package exports the shell messages (`pachiShellMessages`: `it` reference and `en`, namespaces `app`, `auth`, `menu`, `dashboard`, `errors`, `common`; sources in `src/i18n/locales/`) and `composePachiMessages({ generated, overrides, locales, features })` which composes them with the app globs (precedence: shell < generated < overrides < app locales < feature). `setQuasarLang` uses explicit loaders (`src/i18n/quasar-lang-loaders.ts`, one `import('quasar/lang/<pack>.js')` per pack: it works from the app even if the code is in the package). Default languages: `it` (reference), fallback `en`. Initial language: `localStorage` (`pachi-prefs-locale`) > `navigator.languages` (exact, then base language) > `it`; every change is persisted and updates `<html lang>` and the Quasar language (`src/i18n/quasar-lang.ts`, pack lazy-loaded from `node_modules/quasar/lang`). The `PachiLocaleSwitcher` selector is in the `AppBar` (hidden with `QCLI_APP_SHOW_LOCALE_SWITCHER=false` or with a single language). `QCLI_APP_LOCALE=<code>` fixes the language (`fixedLocale` option of `createPachiI18n`): no detection/persistence/selector, a single message set.

**Message convention**: TS objects in `locales/<code>.ts` (the code is the file name: `it.ts`, `en.ts`, `pt-BR.ts`), collected by `import.meta.glob` + `collectLocales`:

- generated by the backend (they stay in the APP): `playground/src/i18n/generated/<language>.json` (`pachifast locale export --base-dir <backend> --dest-path src/i18n/generated --namespace errors.codes`, `--check` to verify they are not stale): they contain `errors.codes.*`, they must not be edited by hand; user overrides in the app's `src/i18n/overrides/<language>.ts|json` (precedence: generated < overrides < app locales < feature);
- shell (in the package): `src/i18n/locales/*.ts` with namespaces `app`, `auth`, `menu`, `dashboard`, `errors`, `common`; apps can add their own in `src/i18n/locales/*.ts` (`locales` glob of `composePachiMessages`);
- feature: `src/features/<name>/locales/*.ts` with namespace = feature name in camelCase (deep merge per language);
- package: `src/locales/*.ts` in the package (sibling folder `<name>`) with its own namespace (e.g. `pachiTable2`).
  `it.ts` is the reference language (the `DefineLocaleMessage` schema derives from it); the others are typed `const en: PachiMessages<typeof it> = {...}` so a missing key is a compile error. Messages are non-precompiled TS objects: the `definePachiQuasarConfig` preset sets `runtimeOnly: false` on the `unplugin-vue-i18n` plugin. In messages the characters `{ } @ |` are special (to write them: `{'@'}`).

**Adding a language in 3 steps**: (1) `pachifq new locale <code>` (creates the files starting from `en.ts`: app, feature and feature; in derived apps there is no `packages/` folder); (2) translate the values (`TODO: translate`); (3) restart the dev server. For packages in `node_modules` the command does not write: add the keys with the same namespace in `src/i18n/locales/<code>.ts`. The languages offered to the user are those present in the app messages (a package cannot add languages on its own).

**Usage**: in the app components `const { t } = useI18n()`; outside `setup()` (stores, helpers, Dialog/Notify) `pachiT('common.goHome', { ...params })`. In packages: `const { t } = usePachiI18n(messages)` in `setup()` with their OWN messages `{ it: {...}, en: {...} }` (from `collectLocales(import.meta.glob('./locales/*.ts', { eager: true, import: 'default' }))`): it registers them only once, without overwriting what the app has already defined for the same key (so the app can redefine a package's texts). Packages do not import root services: they only depend on `@ilpachi/pachi-i18n` (peer). `pachifq new feature` already generates `locales/it.ts` and `en.ts` and pages with `t()`. Complete extraction of the strings already present in the root and in the packages: phase 2 (today they are still hardcoded in Italian).

## Code style

- No trailing semicolon (`semi: never`), single quotes in TS/JS, double quotes in HTML/Vue attributes, 100 characters line width. The lint/format configs (`eslint.config.js`, `oxlint.config.ts`, `stylelint.config.js`, `.oxfmtrc.json`, `.prettierrc*`) are **local and not versioned** (in `.gitignore`, like `*.code-workspace` and `.vscode/`): do not commit them and do not assume they exist; the repo has no `lint`/`format` script.
- `@typescript-eslint/consistent-type-imports`: always `import type` for type-only imports.
- Components in the template in kebab-case (`vue/component-name-in-template-casing`).
- Unused variables/parameters must be prefixed with `_`.
- `pachi` prefix for CSS: all custom CSS variables are `--pachi-*` (e.g. `--pachi-ink`, `--pachi-app-grid-bg`) and all CSS classes defined by our code start with `pachi-` (e.g. `pachi-hub-dash`, `pachi-dc-card`, `pachi-blueprint-card`); Quasar classes/variables (`q-*`, `--q-*`), localStorage keys and `data-*` attributes are not renamed. The same rules apply to ALL `@ilpachi` packages (siblings and `fastquasar-*`): non-`scoped` styles, `--pachi-*` variables with zero-specificity defaults (`:where`, `src/styles/theme-defaults.scss`) so the project that uses them redefines them in its own CSS/SCSS; `!important` only to beat Quasar.
- Icons: always mdi SVGs imported from `@quasar/extras/mdi-v7` and passed as a value (`:icon="mdiCheck"`), never strings ("mdi-check", "close"); for icons coming from data use a resolver with an explicit map.
