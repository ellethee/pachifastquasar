# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> NEL MONOREPO (`pachifastquasar`): questo package sta in `packages/pachifastquasar`, il playground in `/playground` (radice), i comandi `dev`, `build:playground`, `typecheck:playground` si lanciano dalla radice, un solo lockfile e `pnpm-workspace.yaml` in radice. Le "cartelle sorelle" di `settings`/`profile` ora sono `packages/<nome>`; gli altri package arrivano dal registro (niente `overrides link:`). Vedi il `CLAUDE.md` in radice.

## Cos'è

Pacchetto npm `@ilpachi/pachifastquasar` (versione in `package.json`): shell applicativa Vue 3 / Quasar (layout, auth opzionale, dashboard, i18n, router, client HTTP) con dipendenze verso i package riusabili `@ilpachi/*` (gli altri package del monorepo, `packages/<nome>`). Il repo contiene il pacchetto (`src/`, build Vite library mode in `dist/`) e `playground/`, l'app Quasar (`@quasar/app-vite`) che lo consuma, usata per svilupparlo e provarlo. La documentazione pubblica (inglese, MkDocs) sta in `docs/` + `mkdocs.yml` e non è inclusa nel pacchetto npm (`files`); `README.md` e `CHANGELOG.md` sì. Un'app derivata dipende dal pacchetto e ha solo poche righe di configurazione (vedi README, "Uso in un'app"). Nuove feature verticali di un'app vivono in `src/features/**` dell'APP, mai nel pacchetto.

## Comandi

```bash
pnpm install                          # installa root + playground (workspace pnpm; i package @ilpachi del monorepo sono collegati con workspace:*)
pnpm dev                              # playground: compila ./quasar, poi quasar dev (pacchetto dai sorgenti, hot reload)
QCLI_AUTH_ENABLED=false pnpm dev      # senza auth
pnpm test                             # test unitari (Vitest, cartella tests/, alias src/)
pnpm typecheck                        # vue-tsc del pacchetto
pnpm typecheck:playground             # vue-tsc del playground
pnpm build                            # pacchetto: vite build + entry ./quasar (vite.config.node.ts) + dist/styles.css e dist/scss (scripts/build-styles.mjs)
pnpm build:playground                 # build del pacchetto e del playground con il pacchetto da dist/ (PACHI_PLAYGROUND_DIST=true)
QCLI_AUTH_ENABLED=false pnpm -C playground build   # build del playground (pacchetto dai sorgenti)
```

Gli altri package si buildano nella loro cartella `packages/<nome>` (`pnpm typecheck`, `pnpm build`). La pubblicazione avviene solo con `pnpm release <nome> <incremento>` + `git push --follow-tags` (vedi CLAUDE.md di radice): mai `npm publish` a mano.

## Architettura

### Pacchetto vs playground vs app derivate vs features

- `src/` è il pacchetto: nessun `#q-app`, nessun `import.meta.glob` su file dell'app, nessun `import.meta.env` (la config arriva a runtime). Import interni RELATIVI (l'alias `src/` esiste solo per `tests/` e per il codice del playground).
- `src/index.ts` è il barrel (API pubblica). Sotto-percorsi in `exports`: `.`, `./quasar` (entry Node, `src/quasar/`, build separata: non importa Vue), `./styles.css`, `./scss/*`.
- `playground/` (membro del workspace pnpm, dipende dal pacchetto con `link:..`): `quasar.config.ts` (usa `definePachiQuasarConfig`, in dev alias di `@ilpachi/pachifastquasar` verso `src/index.ts`, con `PACHI_PLAYGROUND_DIST=true` usa `dist/`), `src/boot/pachi.ts` (`defineBoot` → `createPachiApp`), `src/router/index.ts` (`defineRouter` → `createPachiRouter` con i glob), `src/stores/index.ts`, `src/pachi-config.ts` (`pachiConfigFromEnv(import.meta.env)` + personalizzazioni), `src/i18n/generated/*.json` (specifici del backend), `src/css/`, `src/features/**`.
- `packages/<nome>` (monorepo): tutti i package `@ilpachi` e il CLI `pachifq` sono in `../<nome>` rispetto a questo package, con versioni indipendenti. I package generici (`pachi-i18n`, `pachi-kit`) hanno build `dist` con Vite library mode; i `fastquasar-*` (legati alla shell ma autonomi negli stili) e il CLI `pachifq` sono package del workspace come gli altri. Le dipendenze tra package del monorepo sono `workspace:^` (peer con i range pubblicati). Componenti pubblicati su npm come `@ilpachi/pachi-kit` (sotto-percorsi `/table`, `/dialog`, `/edit-dialog`, `/fields` con client HTTP iniettabile `setPachiFieldsHttp`, `/uploader`, `/ui`), `fastquasar-settings`, `fastquasar-profile`, `fastquasar-dashboard-widgets`, `pachi-i18n` (i18n con selettore lingua e messaggi per package), `@ilpachi/use-alova` ^2.1.0 (peer, repo ESTERNO `ilpachi/use-alova`: factory HTTP alova con auth/overlay/errori; `createPachiApp` lo cablaggia in `src/app/create-http.ts`) (più il CLI `pachifq`, che copre lo scaffold di nuovi progetti — `pachifq create` —, di nuove feature — `pachifq new feature` — e di nuove lingue — `pachifq new locale <codice>`: genera l'app dai template, che dipendono dal pacchetto senza copiare i sorgenti della shell). Ogni componente ha `peerDependencies` su `vue`/`quasar` (e sugli altri `@ilpachi/*` usati) e viene pubblicato come `dist` (`pnpm build` nel package; `pnpm typecheck` per il solo typecheck). **Non devono importare servizi della shell** (es. `pachi-kit/uploader` accetta `headers`/`eventBus` come prop/composable invece di importare `AuthManager`/`usePachiEventsStore`) — mantiene i package installabili in altri progetti; al massimo `import type` dei contratti (es. `PachiMenuItemFactory`). `pachi-kit/table` usa una factory alova sostituibile (`setPachiAlovaFactory`). Profilo, impostazioni e widget dashboard (attività/sistema) NON sono nella shell: sono i package `fastquasar-profile`, `fastquasar-settings` e `fastquasar-dashboard-widgets`, che il pacchetto non importa. Si installano e si montano in una feature dell'app (`src/features/<nome>/routes.ts`); le dipendenze si iniettano (`setPachiSettingsOptions`, `setPachiWidgetsHttp`, prop `user`, slot `avatar`). Questi tre package sono autonomi negli stili (default `--pachi-*` a specificità zero): usano le variabili `--pachi-*` del progetto se definite. La shell tiene solo la persistenza minima del tema (`ToggleThemeButton`, chiave localStorage `pachi-prefs-theme`). Le route con figli mostrano di default una dashboard di card; `autoDashboard: false` (`QCLI_APP_AUTO_DASHBOARD=false`) la disattiva (la home `/` resta dashboard) e `meta.dashboard` true/false decide per singola route (senza dashboard la route deve avere un componente con `<router-view>` o un `redirect`). Le route possono esporre `meta.widgets` (`{ component, props }[]`). Versioning e pubblicazione: `pnpm release <nome> <incremento>` + `git push --follow-tags`; la pipeline GitHub Actions (`.github/workflows/ci.yml` selettiva, `release.yml` su tag `<nome>@<versione>`, trusted publishing su npmjs) fa il resto.

### Configurazione a runtime (`src/core/config/`)

`IAppConfig` (auth, app, logo, components, menuItems, menuFactories) con default in `defaults.ts`; `setPachiConfig(input)` / `getPachiConfig()` sono il registro letto da componenti, store e router (non esiste più `appConfig` da `import.meta.env`). `pachiConfigFromEnv(env)` mappa `QCLI_*`/`VITE_*` (stesse regole di prima; l'app passa `import.meta.env`). `createPachiApp` e `createPachiRouter` chiamano `setPachiConfig` se ricevono `config` (altrimenti usano quella già impostata): il router è creato PRIMA dei boot file in Quasar, quindi l'app condivide la stessa `pachiConfig` tra router e boot. Lo store di auth risolve `storage` in modo pigro (`lazyStorage`). Personalizzazioni: `logo` (path SVG, `img:`, componente; `PachiLogo`), `components.layout|loginPage|errorPage`, `menuItems` (array o funzione), `menuFactories`.

### Routing (`src/router/`)

`createPachiRouter(options)` (`create-pachi-router.ts`) crea il `Router`: history da `options.mode`/`base` (`hash` default; l'app passa `QUASAR_VUE_ROUTER_MODE/BASE`), albero da `buildPachiRoutes(config, { features, packages, env })` (`routes.ts`), guardia di navigazione. I glob arrivano dall'app (`features`, `packages`, `menus`); `routes-finder.ts` contiene le funzioni pure (ordinamento per `meta.order`, estrazione nome package, `ilpachi-<pkg>-disable-route` da `env`, filtri `meta.root`). `buildPachiRoutes` compone: route core con `meta.root === true` prima, poi auth (se abilitata; `core/auth/pages/routes.ts` è una funzione di `config`), poi feature/package, con catch-all finale. Le route con `meta.root === true` sono top-level (fuori dal layout), le altre figlie del layout; `meta.order` (default 99) ordina il menu. Guardia: auth disabilitata = passa tutto; altrimenti restore silenzioso salvo `meta.noAuth`, redirect a `/auth/login`, `authManager.canAccess(to.meta)` per l'autorizzazione per-route.

### Menu account (`src/core/menu/`)

Contratto `PachiMenuItemFactory` (`ctx: { t, router, config, user? }` → voce | array | null): un package esporta `menu.{ts,js}` (o `dist/menu.js`) con default export la factory. `collectPackageMenus(glob, env)` le raccoglie (rispetta `ilpachi-<pkg>-disable-route`), `registerPachiMenus` le registra (lo fa `createPachiRouter` con l'opzione `menus`), `buildMenuItems(ctx)` compone factory dei package + `config.menuFactories` + voci predefinite (solo Home, omessa se una factory fornisce `/`; Profilo e Impostazioni arrivano solo dai package) + `auth.menu.extraButtons` + `config.menuItems`, ordinando per `order` (default 50). La visibilità e l'esistenza della route sono valutate dal componente.

### Boot e alias v3

La shell non ha boot file: `createPachiApp(ctx, { config, messages })` (`src/app/create-pachi-app.ts`, alias `pachiBoot`) imposta la config, crea il client HTTP (`@ilpachi/use-alova` ^2.1.0: alova + fetch) con `token`/`authType` da `AuthManager` (token solo same-origin), refresh del token su 401 con `retry()`, overlay `auto` con delay 300 ms via Quasar `Loading`, messaggi di errore via Quasar `Dialog`, `cacheFor: { GET: null }` e `unwrapEnvelope` da `http.envelope` (`QCLI_HTTP_ENVELOPE=false` per backend con `PACHIFAST_ENVELOPE_ENABLED=false`) (le classi usano `getUseAlovaInstance()({ url }).alova`; opzioni per richiesta via `meta`: `{ meta: { autoError: false, spinner: false } }`, alias letti da use-alova), installa i18n e la classe `pachi-hover-fx-disabled`. L'app lo avvolge in `playground/src/boot/pachi.ts` (`defineBoot`). Login: `AuthManager.login` restituisce `{ mfaRequired }` (con MFA il `mfa_token` resta solo in memoria) e `verifyMfa(code)` chiude il secondo step (`POST /api/mfa/verify`); refresh token rotanti (il nuovo sostituisce il vecchio, riletto dallo storage per le più schede) e logout con `{ refresh_token }`. `createPachiApp` fa `provide('pachiLogout')` (`PACHI_LOGOUT_KEY`, logout locale senza richieste, per `fastquasar-profile` dopo il cambio password). Pinia: `createPachiPinia()` (con `pinia-plugin-persistedstate`) in `src/stores/index.ts` dell'app.

`definePachiQuasarConfig(overrides?, options?)` (`src/quasar/`) è il preset di `quasar.config.ts` (boot `pachi`, `css` con `~@ilpachi/pachifastquasar/styles.css`, extras roboto, SPA, `extendViteConf` con `envDir`/`envPrefix ['VITE_','QCLI_']`, `cssMinify 'esbuild'`, alias v2 `src/ assets/ boot/ stores/ features/` (Quasar v3 non li ha più), `resolve.dedupe` dei singleton, plugin `@intlify/unplugin-vue-i18n/vite` (`runtimeOnly: false`, include `src/i18n`) e `vite-plugin-checker`, `extendTsConfig` con `src/*`, proxy `/api` verso `QCLI_PROXY_TARGET`, framework `svg-mdi-v7` + Dialog/Notify/Loading/Dark). Merge degli override: oggetti ricorsivo, array concatenati, `extendViteConf`/`extendTsConfig` in sequenza. Tipizzato in modo strutturale (non importa `#q-app`). Se serve un nuovo alias di primo livello: opzione `aliases`. `tsconfig.json` del playground è solo `{ "extends": "./.quasar/tsconfig.json" }` — i path si configurano nel preset.

### Logo e favicon

`pachiLogo` (`src/extras/pachi-icons/index.ts`) e' `img:` + URL di `src/assets/logo/logo.svg` (mascotte Pachi, colori fissi). In lib mode Vite inlina gli asset in base64 sempre (anche `assetsInlineLimit: 0`): il plugin `pachiLogoAsset` in `vite.config.ts` (con rolldown il data URL e' `new URL("data:...", "" + import.meta.url)`, la regex accetta entrambe le forme) sostituisce il data URL con `new URL("./assets/logo.svg", import.meta.url)` ed emette `dist/assets/logo.svg`; l'app consumatrice (dev/build) lo risolve con il suo Vite. Non rimettere `?inline`/base64. I favicon e i comandi di rigenerazione (vtracer + svgo + inkscape) sono in `src/assets/logo/` (README); i favicon vanno in `playground/public/` e in `pachifq/templates/app/public/`, non nel pacchetto. `pachiLogoDuotone` e' deprecato.

### Stili

Il layout è alto un viewport e non scrolla. Scroll opt-in: `meta.pageScroll` avvolge l'intera pagina in `.pachi-page-scroll` (scroll verticale entro `--pachi-page-height`); il componente `PachiScrollArea` (`src/core/components/`) fa scrollare solo il contenuto alto dentro una pagina, occupando lo spazio sotto di sé fino al limite inferiore (misura con `getBoundingClientRect`, resize + ResizeObserver).

`src/scss/` → `dist/styles.css` (compilato da `scripts/build-styles.mjs`) + `dist/scss/*` (sorgenti). `quasar-variables.scss` (palette Sass di Quasar, valori `!default`: l'app definisce gli override e poi fa `@import '@ilpachi/pachifastquasar/scss/quasar-variables'` nel proprio `src/css/quasar.variables.scss`), `tokens.scss` (token `--pachi-*`, `$dark-page/$light-page/$light-color` configurabili con `@use ... with`), `app.scss` (+ blueprint/bento/quasar-hacks/...), `fonts.scss`. Gli stili dei componenti `.vue` sono iniettati nel JS dal plugin `vite-plugin-css-injected-by-js`.

### Servizi (`src/services/*/`)

Pattern comune: cartella con `index.ts` (barrel), `<nome>-manager.ts` (classe/logica), `<nome>-store.ts` (stato Pinia), `types/` (file `.ts`, non `.d.ts`: devono arrivare in `dist`). Presenti: `auth-manager` (singleton `AuthManager.getInstance()`: token/refresh con auto-renew 60s prima della scadenza, header di auth per Alova, WebSocket lazy con ticket monouso), `ws-manager`. Il client HTTP (`createUseAlova`, `getUseAlovaInstance`, `ResponseError`, `STOP_PROCESSOR`) vive in `@ilpachi/use-alova` (`withFiles` da `@ilpachi/use-alova/files`): importare da lì. Il `settings-manager` vive in `@ilpachi/fastquasar-settings`.

### i18n

Package `@ilpachi/pachi-i18n` (vue-i18n 11, composition, `legacy: false`). `createPachiApp` chiama `createPachiI18n({ messages, fixedLocale, onLocaleChange: setQuasarLang })` — nient'altro da cablare. Il pacchetto esporta i messaggi della shell (`pachiShellMessages`: `it` riferimento e `en`, namespace `app`, `auth`, `menu`, `dashboard`, `errors`, `common`; sorgenti in `src/i18n/locales/`) e `composePachiMessages({ generated, overrides, locales, features })` che li compone con i glob dell'app (precedenza: shell < generated < overrides < locales dell'app < feature). `setQuasarLang` usa loader espliciti (`src/i18n/quasar-lang-loaders.ts`, un `import('quasar/lang/<pack>.js')` per pack: funziona dall'app anche se il codice è nel pacchetto). Lingue di default: `it` (riferimento), fallback `en`. Lingua iniziale: `localStorage` (`pachi-prefs-locale`) > `navigator.languages` (esatto, poi lingua base) > `it`; ogni cambio viene persistito e aggiorna `<html lang>` e la lingua di Quasar (`src/i18n/quasar-lang.ts`, pack caricato lazy da `node_modules/quasar/lang`). Il selettore `PachiLocaleSwitcher` è nella `AppBar` (nascosto con `QCLI_APP_SHOW_LOCALE_SWITCHER=false` o con una sola lingua). `QCLI_APP_LOCALE=<codice>` fissa la lingua (opzione `fixedLocale` di `createPachiI18n`): nessun rilevamento/persistenza/selettore, un solo set di messaggi.

**Convenzione messaggi**: oggetti TS in `locales/<codice>.ts` (il codice è il nome del file: `it.ts`, `en.ts`, `pt-BR.ts`), raccolti da `import.meta.glob` + `collectLocales`:

- generati dal backend (restano nell'APP): `playground/src/i18n/generated/<lingua>.json` (`pachifast locale export --base-dir <backend> --dest-path src/i18n/generated --namespace errors.codes`, `--check` per verificare che non siano vecchi): contengono `errors.codes.*`, non vanno modificati a mano; override dell'utente in `src/i18n/overrides/<lingua>.ts|json` dell'app (precedenza: generated < overrides < locales dell'app < feature);
- shell (nel pacchetto): `src/i18n/locales/*.ts` con namespace `app`, `auth`, `menu`, `dashboard`, `errors`, `common`; le app possono aggiungerne di propri in `src/i18n/locales/*.ts` (glob `locales` di `composePachiMessages`);
- feature: `src/features/<nome>/locales/*.ts` con namespace = nome feature in camelCase (merge profondo per lingua);
- package: `src/locales/*.ts` nel package (cartella sorella `<nome>`) con namespace proprio (es. `pachiTable2`).
  `it.ts` è la lingua di riferimento (da lì deriva lo schema `DefineLocaleMessage`); le altre sono tipizzate `const en: PachiMessages<typeof it> = {...}` così una chiave mancante è un errore di compilazione. I messaggi sono oggetti TS non precompilati: il preset `definePachiQuasarConfig` imposta `runtimeOnly: false` sul plugin `unplugin-vue-i18n`. Nei messaggi i caratteri `{ } @ |` sono speciali (per scriverli: `{'@'}`).

**Aggiungere una lingua in 3 passi**: (1) `pachifq new locale <codice>` (crea i file partendo da `en.ts`: app, feature e feature; nelle app derivate non esiste una cartella `packages/`); (2) traduci i valori (`TODO: traduci`); (3) riavvia il dev server. Per i package in `node_modules` il comando non scrive: aggiungere le chiavi con lo stesso namespace in `src/i18n/locales/<codice>.ts`. Le lingue offerte all'utente sono quelle presenti nei messaggi dell'app (un package non può aggiungere lingue da solo).

**Uso**: nei componenti dell'app `const { t } = useI18n()`; fuori da `setup()` (store, helper, Dialog/Notify) `pachiT('common.goHome', { ...params })`. Nei package: `const { t } = usePachiI18n(messages)` in `setup()` con i PROPRI messaggi `{ it: {...}, en: {...} }` (da `collectLocales(import.meta.glob('./locales/*.ts', { eager: true, import: 'default' }))`): li registra una sola volta, senza sovrascrivere ciò che l'app ha già definito per la stessa chiave (l'app può quindi ridefinire i testi di un package). I package non importano servizi del root: dipendono solo da `@ilpachi/pachi-i18n` (peer). `pachifq new feature` genera già `locales/it.ts` e `en.ts` e pagine con `t()`. Estrazione completa delle stringhe già presenti nel root e nei package: fase 2 (oggi sono ancora in italiano fisso).

## Stile codice

- Niente punto e virgola finale (`semi: never`), apici singoli in TS/JS, doppi apici negli attributi HTML/Vue, 100 caratteri di larghezza riga. I config di lint/format (`eslint.config.js`, `oxlint.config.ts`, `stylelint.config.js`, `.oxfmtrc.json`, `.prettierrc*`) sono **locali e non versionati** (in `.gitignore`, come `*.code-workspace` e `.vscode/`): non committarli e non assumere che esistano; il repo non ha script `lint`/`format`.
- `@typescript-eslint/consistent-type-imports`: sempre `import type` per i soli tipi.
- Componenti nel template in kebab-case (`vue/component-name-in-template-casing`).
- Variabili/parametri inutilizzati vanno prefissati con `_`.
- Prefisso `pachi` per CSS: tutte le variabili CSS custom sono `--pachi-*` (es. `--pachi-ink`, `--pachi-app-grid-bg`) e tutte le classi CSS definite dal nostro codice iniziano per `pachi-` (es. `pachi-hub-dash`, `pachi-dc-card`, `pachi-blueprint-card`); non si rinominano classi/variabili Quasar (`q-*`, `--q-*`) né chiavi localStorage o attributi `data-*`. Le stesse regole valgono per TUTTI i package `@ilpachi` (sorelle e `fastquasar-*`): stili non `scoped`, variabili `--pachi-*` con default a specificità zero (`:where`, `src/styles/theme-defaults.scss`) così il progetto che li usa li ridefinisce nei propri CSS/SCSS; `!important` solo per battere Quasar.
- Icone: sempre SVG mdi importate da `@quasar/extras/mdi-v7` e passate come valore (`:icon="mdiCheck"`), mai stringhe ("mdi-check", "close"); per icone che arrivano da dati usare un resolver con mappa esplicita.
